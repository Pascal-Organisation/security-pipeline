| D-57 | 2026-11-25, owner: private repos on the Free plan exhausted the 2000 free GitHub-hosted minutes (private repos only), so every PR went red. Only two jobs of `ci.yml` still ran GitHub-hosted for private callers: `visibility` and `security-gate` (1 billed minute each per run, about 450 min/month in homelab alone). Cause of the earlier impression that private work fell back to hosted minutes: jobs skipped because `visibility` failed still show the label `ubuntu-24.04` (their `needs` output is empty, so the expression falls to the hosted label) but never start and are not billed; only `visibility` and `security-gate` actually ran hosted (checked on homelab runs 2026-11-18..23). The fallback is still the wrong default to rely on: a failed `visibility` skips everything and fails the gate, it does not move work to hosted. Both now use `runs-on: ${{ github.event.repository.private == true && inputs.runner || 'ubuntu-24.04' }}`. In a reusable workflow `github.event` is the caller's event payload; `repository` is the BASE repository, set by GitHub, not influenced by a fork's author, and present on pull_request, push, schedule, workflow_dispatch. Fail-safe direction: only a literal boolean `true` selects the self-hosted label; missing, null or false give `ubuntu-24.04`, so a public repo cannot reach the cluster through a missing field. `visibility` keeps its API check (now on the resolved runner) and FAILS when the payload says private but the API says public, so the route of all other jobs (still by API answer) and the gate cannot silently pass on a wrong decision. `security-gate` keeps `if: always()` and `visibility` stays in its `needs`, so a failed or skipped `visibility` still fails the gate. `build-container.yml` job `policy` (Release policy, read-only token, no secrets, no signing identity) uses the same expression; `publish`, `sign` (signing identity, D-2, `runners.md`: signing never self-hosted) and `sbom-upload` stay GitHub-hosted. Supersedes the header remark that the payload is not relied on, for these two jobs only. Residual risk: if the payload were wrong in the private direction for a public repo, the tiny `visibility` job (read-only token, curl and jq) would start on the cluster before it fails; the runner groups still exclude public repositories (`allows_public_repositories=false`, G-C1), so the job would stay queued there. Failure mode: private caller with the runner cluster down: the gate job waits for a runner (no hosted fallback) and the check stays pending until cancelled (fleet-reaper after 24 h); it never passes, which is the safe direction.
